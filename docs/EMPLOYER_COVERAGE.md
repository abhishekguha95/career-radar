# Employer coverage pilot

Research date: 2026-10-22, Asia/Kolkata. This is a small source-coverage study for the India & Global Remote and Europe Relocation tracks, not a shortlist or a claim of candidate eligibility. An accessible feed does not establish that every record is a current vacancy, that a role is relevant, or that sponsorship is offered. Counts describe the responses observed, not the whole hiring market.

The three Greenhouse checks used one GET each against `https://boards-api.greenhouse.io/v1/boards/{verified-board}/jobs?content=true`, a 10-second timeout, redirect rejection and an 8 MiB response cap. All three responses fit the cap and matched their declared totals. These checks inspected responses without writing postings to PostgreSQL. No real posting descriptions or raw response files were committed.

Coverage result: one verified Lever board, three verified Greenhouse boards, one verified unsupported Ashby board and three unresolved integrations in this eight-employer pilot. Greenhouse materially expands reachable employer coverage across both tracks. This does not measure matching accuracy or guarantee relevant openings. Pune-specific employers, Norway, the Netherlands and Germany beyond incidental multi-country feeds need further research; the pilot is not a complete target list.

## Connector contract and access review

Reviewed [Greenhouse Job Board API documentation](https://docs.greenhouse.io/job-board.html). Its GET endpoints expose public board data without authentication; no Harvest account, application POST, paid key or candidate endpoint is needed. This establishes the documented read path, not unrestricted redistribution rights. Keep collection local, paced and bounded; review terms again before public republication or expanding use.

- Use the job posting's numeric `id`, converted losslessly to a string, as external identity. Do not substitute `internal_job_id`, requisition ID or title; internal IDs may be absent and can group multiple postings.
- Use the documented list endpoint with `content=true`. It returns a jobs envelope and `meta.total`, rather than Lever's skip/limit pagination. Validate totals and response bounds. Preserve partial results when enumeration is explicitly incomplete; never claim all jobs found after a cap or malformed record.
- Map supplied `first_published` as the source's first-published timestamp when present; preserve `updated_at` separately. The detail example documents `first_published`, and all three observed list payloads also supplied that field. Missing publication dates remain unknown. Collection time is a separate observation.
- Retain `absolute_url` as the job/application-page URL without manufacturing an application endpoint. Preserve descriptions as plain text and raw payloads in local snapshot history. Keep unsupported geography/workplace/employment attributes unknown; a remote title or office name alone must not create India eligibility.
- Use the documented fixed `boards-api.greenhouse.io` host. The application source region is `global` for this endpoint, independently of the employer/job's country. Additional regional endpoints require separate verification.
- Reuse existing pacing (250 ms), timeout (10 seconds), response cap (8 MiB), at most three attempts, cancellation and terminal-access-error behavior. Respect Retry-After; do not evade restrictions. At this size a single feed request is sufficient; if future boards exceed bounds, expose that gap and revisit the collection design.

## Small implementation increment

Add Greenhouse alongside Lever in runtime input/output contracts, the CLI and a new migration extending the existing provider constraint. Keep all six domain tables and existing source/posting uniqueness. Share bounded JSON transport and HTML-to-text handling to keep both adapters' protections consistent. Add provider-specific mapping/fetch tests and isolated PostgreSQL/API tests for identity, repeat sightings, history, partial results and provider separation. No dependency upgrade is needed.

For the first real-data review, use the existing exact source filter from `/sources`. It excludes other sources from the job list; dashboard cards remain explicitly workspace-wide totals, including demos. This is a single-source pilot view, not a combined multi-employer real-search mode. A shared source-purpose contract and consistently scoped metrics/ranking remain a separate decision. Do not delete demonstration data or redefine LIVE to imply authenticity.

After offline checks, run a bounded collection and repeat against verified Greenhouse employer boards. Record actual outcomes and source IDs in VERIFICATION. Profiles, expanded eligibility rules, ranking, combined real-search views, Ashby and daily scheduling are subsequent increments; their absence must remain explicit.

Implementation outcome: the described Greenhouse increment is implemented. Local collections retained all 143 Grafana, 26 Razorpay and 202 Wolt records; a second collection of each returned all records unchanged, with zero rejected records and no additional postings or snapshots. Original sample/demo sources were preserved. Current evidence and source IDs are in [VERIFICATION](VERIFICATION.md). These 371 records span all departments and locations in those feeds; they are not 371 profile matches or verified actionable vacancies.
