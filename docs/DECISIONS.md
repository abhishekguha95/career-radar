# Engineering decisions

Plan approved 2026-10-21. Record changes here with supporting evidence; do not treat tool preferences as permanent constraints.

| Decision | Choice and rationale | Alternative / revisit condition |
| --- | --- | --- |
| D001: boundaries | TypeScript modular monolith; NestJS API and separate CLI share modules. Explicit validation and DI; ingestion does not block HTTP requests. | Fastify alone is smaller; Next.js route handlers reduce app count. Revisit if Nest ceremony outweighs module/testing value. |
| D002: services | PostgreSQL only; source-scoped database locking serializes runs. No persistent scheduler in Phase 1. | Redis/BullMQ when durable queued scheduling, independent workers, or retry coordination is actually needed. |
| D003: provider | Original TypeScript Lever adapter. Official [docs](https://github.com/lever/postings-api) permit third-party scraping of published posts and expose pagination, workplace type, commitment, and posting/apply URLs. | Greenhouse provides richer source dates/identities. Revisit based on target-employer coverage. Python reuse adds runtime and integration work for one simple API. |
| D004: storage | PostgreSQL 18 supported stable line; pg and stable node-pg-migrate. Parameterized SQL exposes constraints, locking and transaction behavior. | Drizzle/Prisma provide stronger inferred/generated query types. Revisit as query volume grows; SQL requires integration tests and explicit row mapping. |
| D005: identity/history | Unique source + external ID. Initially one opportunity per posting. Append snapshots when source content changes; observation timestamps are separate. | No fuzzy merges until a review workflow and evidence exist. No auto-closure from missing posts in Phase 1. |
| D006: geography | Narrow versioned INDIA_REMOTE signal; conflicting or vague evidence means UNKNOWN. Evidence refers to a preserved posting snapshot. | No overall application or visa verdict. Expand only against reviewed examples and false-positive measurements. |
| D007: UI | Deferred until ingestion/API correctness; README and API examples are the initial demo. | Add a small Next.js client only if it materially helps review and remains low complexity. |
| D008: license | Preserve existing MIT license for original work. No upstream source copied. | Each future reuse needs file-specific license/dependency and notice review. Dorker currently has conflicting README/license statements. |
| D009: tool versions | Pin npm-verified compatible releases and commit pnpm lockfile. TypeScript 6.0.3 instead of latest 7.0.2: typescript-eslint 8.72.0 requires TypeScript <6.1.0. Node 24 is the runtime target. | Upgrade after peer-range checks and regression tests, rather than selecting latest versions independently. |
| D010: local execution | Owner clarified 2026-10-21: Compose runs PostgreSQL only; API and ingestion JavaScript run on the host during local development. | Containerize API/worker later. Redis is a future addition when queued work justifies it. No API/worker Dockerfiles in Phase 1. |
| D011: source environments | Source uniqueness includes FIXTURE/LIVE mode as well as provider/region/site, preventing fixture replays from modifying live postings even when a site name matches. | Extra source rows are intentional; API must expose mode so demo data is distinguishable. |
| D012: stale observations | An older observation cannot overwrite different newer content. Identical old replays cannot regress last-seen time. Hash raw + normalized content + mapping version using sorted JSON keys. | Revisit if an explicit historical-import workflow is added; such imports should not silently replace current state. |
| D013: observation vs change | Store latest fetch provenance on the posting separately from preserved snapshot provenance. An unchanged fetch updates observation freshness but does not add another content version. | Add a per-posting observation ledger only when audit/query needs justify its storage cost. |
| D014: geography precision | Version india-remote-v1 recognizes a small whitelist of complete permission/residence-exclusion statements; preserved passages include exact normalized-text offsets. Vague geography, relocation wording, qualifiers, and conflicts stay UNKNOWN. | This sacrifices recall deliberately. Expand recognized forms only with reviewed positive/negative examples; never treat the signal as overall eligibility or visa advice. |
| D015: revised sequence | Owner approved making the UI Phase 2, ahead of employer coverage, profiles, evaluation and ranking. Build browsing/evidence/source visibility from persisted data. | No fictional ranking scores, save/apply actions or speculative integrations; later capabilities follow their reviewed requirements. |
| D016: frontend boundary | Next.js App Router reads the NestJS API on the server, with no direct database access. URL parameters preserve filters/selection. Server fetches use no-store and timeouts; browser navigation stays on the frontend origin. | Direct browser fetch would require CORS and additional client error/cache state. A Vite client would be lighter; Next.js fits the originally preferred frontend and its server-rendered read boundary. |
| D017: sources and counts | Add GET /sources with actual posting counts and latest run state. Overview metrics use all stored source data, not a page's partial results. | Avoid inferring global health/counts from the visible jobs page. No new tables or ingestion controls are required. |
| D018: local npm commands | Provide npm run setup, db:start, backend and frontend. Startup scripts bootstrap pinned pnpm internally; no global pnpm installation is required. Backend builds its dependency chain before starting; frontend uses Next's dev server. | Separate terminals keep logs and lifecycle simple. Retain existing pnpm commands for contributors. |

Phase 2 dependency metadata checked on npm: Next.js 16.4.2 (Node >=20.9), React/React DOM 19.3.1, React types 19.3.0, lucide-react 1.60.0 (ISC). The initially selected lucide-react 1.61.0 was rejected by the workspace's 24-hour release-age policy; 1.60.0 meets that policy and the same peer requirements. Their peer ranges are compatible with the Node 24/TypeScript 6 workspace. Next.js [installation](https://nextjs.org/docs/app/getting-started/installation) and [TypeScript configuration](https://nextjs.org/docs/app/api-reference/config/typescript) were checked. No remote Sites registration or deployment is part of this local-only work.

Lever was selected to validate the foundation, not from a completed employer-coverage study. Compare actual target-employer coverage before choosing subsequent providers. Public API fields and access documentation are stronger initial evidence than a scraper library's popularity.

Runtime/peer metadata was queried from npm on 2026-10-21: pnpm 12.14.0; NestJS 12.2.0 (Node >=20); pg 8.23.1; node-pg-migrate 9.0.0 (Node >=20.11); Zod 4.6.7; Vitest 5.0.5 (supports Node 24); ESLint 10.13.0 and typescript-eslint 8.72.0. The local Node 24.3.0 satisfies these ranges. Install/build verification is recorded separately.
